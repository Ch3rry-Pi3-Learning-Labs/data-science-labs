# Writing and Accessibility Guide

## Voice

Use a friendly, calm and collaborative voice. Write as though an experienced practitioner is guiding an intelligent reader who is new to the specific subject.

- Prefer direct sentences and familiar words.
- Explain necessary technical language; do not remove it.
- Avoid implying that a concept is “obvious”, “trivial” or “easy”.
- Do not confuse brevity with accessibility: a missing reasoning step is still missing.
- Use British English in explanatory prose.

## Acronyms and abbreviations

Write out an acronym at first use and give the abbreviated form in parentheses:

> stochastic gradient descent (SGD)

After that, the abbreviation may be used consistently. Define conventional evaluation abbreviations such as true positive (TP), false positive (FP), true negative (TN) and false negative (FN) before using them in formulas.

## Beginner-friendly explanations

For a difficult idea, aim to provide:

1. an intuitive description;
2. the formal definition;
3. a small example;
4. the code representation; and
5. a limitation or common misunderstanding.

Analogies may support the formal explanation but should never replace it.

## Reader assumptions

State the intended audience and prerequisite knowledge near the beginning. If a notebook depends on calculus, linear algebra, probability or Python behaviour, link or briefly recap the necessary concept.

## Accessibility checks

- Never use colour as the only carrier of meaning.
- Provide text interpretations of figures and outputs.
- Use descriptive link text.
- Keep headings hierarchical.
- Avoid excessively wide tables and code outputs.
- Include alt text when Markdown or the publication platform supports it.
- Explain notation before asking the reader to manipulate it.
